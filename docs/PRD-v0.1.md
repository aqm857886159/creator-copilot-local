## 1. 产品结论

### 1.1 产品定位

面向深度口播创作者的本地优先内容生产系统：连接账号洞察、选题、脚本、分镜、拍摄素材、AI 粗剪、剪映精修、发布和复盘。

产品不与剪映正面竞争，不复制其庞大的模板、素材和特效生态，而是负责内容理解、素材组织、剪辑编排和生产数据沉淀。

一句话定位：

> AI 负责理解和编排内容，剪映负责成熟的人工精修，我们负责把创作全流程连起来。

### 1.2 第一切入场景

第一阶段聚焦抖音真人深度口播内容：创作者通过真人讲观点建立信任，但画面容易单调、素材难找、补拍缺少明确指导、剪辑耗时。

首个完整闭环：

```text
账号/对标分析 → 选题建议 → 脚本 → 分镜 → 补拍任务 → 素材归档 → AI 粗剪 → 剪映精修 → 发布 → 复盘记忆
```

产品底层对象保持通用，未来可以扩展到知识类、访谈、测评、播客切片和其他平台，而不是把模型写死为“口播视频”。

## 2. 已确认的产品约束

1. AI 剪辑不做剪映的完整替代品；优先做 AI 剪辑计划、素材匹配、粗剪和外部编辑器桥接。
2. 首期同时考虑 Windows 与 macOS，但剪映草稿适配必须建立独立的系统/版本矩阵。
3. 首期支持视频、音频、字幕、基础文本、基础转场和素材路径；复杂花字、模板和高级效果交给剪映。
4. 所有核心能力同时提供 UI 入口、结构化 API 和 Agent Tool/MCP 入口。
5. 我们自己的项目数据是唯一事实源；剪映是外部精修工具，不是账号、脚本、素材和复盘数据的主数据库。
6. 拍摄采用 A 方案：软件生成分镜拍摄任务，用户用手机/相机拍摄，再通过导入或监控文件夹回传；不控制手机、相机或电脑摄像头。

## 3. 用户与核心问题

### 3.1 核心用户

- 抖音真人口播创作者；
- 个人创作者、小型内容团队；
- 有观点、有脚本能力，但缺乏稳定拍摄和剪辑工作流的人；
- 已经使用剪映，不希望被迫迁移到一个不成熟编辑器的人。

### 3.2 关键痛点

- 写出观点后，无法自然拆成有画面变化的分镜；
- 个人素材很多，但无法按“这句台词需要什么画面”来检索；
- 没有素材时，不知道该补拍什么、拍多长、怎么拍；
- 口播需要提词器，拍摄和脚本脱节；
- AI 生成视频通常是黑盒结果，难以继续修改；
- 剪辑完成后，数据没有回流到下一次选题和脚本。

## 4. 产品工作流

### 4.1 账号与机会

- 维护自己的账号档案：定位、受众、内容支柱、语气、禁用表达、历史表现；
- 接入 TikHub 或其他数据源，获取对标账号、热点、作品和互动指标；
- 输出机会卡：用户痛点、内容缺口、可切入角度、参考作品和风险提示；
- 机会卡一键转为选题卡。

### 4.2 选题与脚本

- 选题库支持来源、标签、状态、优先级、证据和复盘关联；
- AI 生成多个切入角度，不只生成标题；
- 文本编辑器支持观点、论据、案例、反例、结论、CTA 等结构化段落；
- 生成脚本时同时生成预估时长、强调词和可视化需求；
- 提词器模式支持段落、字号、速度、镜头提示和停顿标记。

### 4.3 分镜与补拍任务（A 方案）

每条脚本可生成多个 Shot 对象。每个 Shot 包含：

- 对应台词或观点；
- 画面目的：解释、举证、转场、情绪、节奏重置；
- 景别、构图、机位、镜头运动；
- 建议时长和可接受时长区间；
- 拍摄方式：手机、相机、屏录、现有素材或 AI 生成；
- 参考示意图和文字说明；
- 是否出镜、是否需要口播、是否需要道具；
- 完成状态和素材关联。

用户可以逐条完成任务，也可以批量拍摄后统一导入。系统不控制拍摄设备，只负责指导、归档、检查和调用。

### 4.4 素材库

素材导入后自动生成：

- 文件指纹、代理文件、缩略图和波形；
- ASR 转写、时间码和关键词；
- 场景、人物、物体、景别、方向、情绪、光线、动作等标签；
- 权属和来源信息；
- 与 Shot、脚本、项目和历史成片的关联；
- 可人工修正的标签。

搜索必须支持自然语言，例如“找一个 3 秒以内、竖屏、手部翻书、适合放在‘举例’这一句后面的镜头”。

### 4.5 AI 粗剪

AI 先输出“剪辑提案”，经用户确认后写入自有时间线：

- 主口播轨；
- B-roll 和补拍镜头；
- 字幕轨；
- 基础文本/标题轨；
- BGM 与音效轨；
- 节奏、停顿、转场和标记；
- 每个决策的素材来源、脚本依据和置信度。

所有 AI 操作必须可预览、可撤销、可比较，不允许一次性覆盖用户原项目。

## 5. AI 能力与工具契约

内置 Agent、UI 和外部 MCP 都调用同一组能力，不维护三套逻辑。

### 5.1 能力注册表

### 5.2 Tool 调用规则

- 输入输出使用版本化 JSON Schema；
- 编辑类操作默认返回 proposal，不直接提交；
- 用户确认后以一个可撤销事务提交；
- 导出、删除、外部发布等副作用操作需要显式确认；
- 每次操作记录 provenance：谁调用、使用了什么模型、使用了哪些素材、生成了什么结果；
- AI 不直接拼接或手写剪映草稿 JSON，而是调用导出适配器。

## 6. 剪辑格式与导出方案

### 6.1 事实判断：不要把剪映原生草稿误写成 XML

FCPXML 是 Apple Final Cut Pro 的通用时间线交换格式，可描述媒体、剪辑决策、项目和元数据；它不是剪映原生工程格式。[Apple FCPXML Reference](https://developer.apple.com/documentation/professional-video-applications/fcpxml)

剪映/CapCut 官方公开说明目前不支持直接导入或导出 Premiere 等第三方工程文件，跨项目通常需要导出完整视频后再次导入，图层和效果会被合并。[CapCut 官方说明](https://www.capcut.com/help/how-do-i-export-pro-project)、[跨草稿导入说明](https://www.capcut.com/help/import-a-previous-project-into-the-current-project)

社区逆向项目显示，剪映草稿常见为草稿目录 + JSON 资源引用；部分版本对 `draft_content.json` 加密，且版本升级会导致生成和批量导出兼容性变化。[pyJianYingDraft](https://github.com/yuanmouren1hao/pyjianyingdraft)

因此产品需要同时支持三类输出：

1. 剪映草稿适配器：目标是可打开、可继续编辑，不承诺跨所有版本稳定；
2. FCPXML：面向 Final Cut Pro 和其他支持 FCPXML 的工具；
3. 通用交付包：MP4 + SRT + 原始/代理素材清单 + `project-manifest.json`。

### 6.2 剪映适配器设计

适配器按目标产品和版本拆分：

```text
jianying-cn-windows
jianying-cn-macos
capcut-intl-windows
capcut-intl-macos
fcpxml
```

每个适配器必须有：

- 支持的版本范围；
- 支持的字段和效果清单；
- 不支持字段的降级策略；
- 素材复制/路径重写策略；
- 导出后自动校验和打开指引；
- 失败时生成通用交付包；
- 真实样例项目回归测试。

首期建议使用“用户选择剪映草稿目录/导出目录”的显式方式，不依赖未经验证的系统路径猜测。

### 6.3 清晰度、帧率和编码：默认预设不等于能力上限

项目必须把输出规格作为一等配置。默认值用于降低决策成本，但用户必须能够进入高级设置，按自己的目标格式输出。产品不能把“抖音 1080p”做成唯一出口。

CapCut 的导出界面本身就是这种模式：用户可以调整分辨率、帧率、格式、编码器和码率，并根据设备和素材能力动态显示可用选项。[CapCut 导出设置说明](https://www.capcut.com/resource/how-to-use-capcut)、[CapCut 桌面端导出说明](https://www.capcut.com/resource/capcut-desktop-download)

#### 输出对象分为三层

1. **项目规格（Project Settings）**：画布尺寸、比例、时间基准、帧率、色彩空间。它影响时间线和剪映/FCPXML 工程。
2. **渲染规格（Render Settings）**：容器、视频编码器、质量/码率、音频编码、硬件编码器。它影响 MP4/MOV 等成片文件。
3. **交换规格（Exchange Settings）**：剪映草稿、FCPXML、项目清单。交换文件主要描述时间线和素材引用，本身不等于最终视频编码。

#### 默认预设

- 抖音竖屏：1080 × 1920、9:16、继承主口播帧率、H.264、MP4、AAC 48 kHz；
- 高质量竖屏：按源素材设置画布，保持源帧率，较高码率；
- 4K 母版：源素材支持时保留 4K，优先高质量编码；
- 无损/中间文件：根据操作系统和本地编码能力提供 ProRes、DNx、无损图像序列等可选项；
- 仅音频：WAV、MP3、FLAC 等可用格式；
- 字幕包：SRT、VTT、ASS，以及烧录字幕或独立字幕两种方式。

#### 高级自定义

用户至少可以自定义：

- 容器：MP4、MOV、WebM、MKV 等后端支持的格式；
- 视频编码：H.264、H.265/HEVC、AV1，以及系统可用的专业编码器；
- 分辨率：常用预设 + 自定义宽高 + 锁定/解除比例；
- 帧率：跟随源素材、跟随项目或手动设置；
- 码率控制：推荐、VBR、CBR、CRF/质量优先等后端支持的方式；
- 音频编码、采样率、声道、码率和是否导出独立音轨；
- 硬件编码、软件编码、代理渲染和并发数；
- 文件命名、目录、封面帧和版本号。

这里的“支持所有格式”应理解为：以本地 FFmpeg、系统硬件编码器和具体交换适配器的能力为上限；不支持的组合必须在界面中解释原因，而不是导出后才失败。

OpenChatCut 的做法值得直接借鉴：macOS 优先 VideoToolbox、Windows 优先 NVENC，不可用时回退 CPU；同时提供关闭硬件编码、覆盖编码器、控制并发和导出队列的能力。[OpenChatCut 导出配置](https://github.com/0xsline/OpenChatCut/blob/main/.env.example)

#### 质量检查和能力降级

导出前必须展示质量检查：

- 输出分辨率与源素材分辨率；
- 是否发生缩放、裁切、补帧或变速；
- 是否发生色彩空间转换；
- 是否有离线素材；
- 是否有不支持的花字、字体、特效或音频编码；
- 预估文件大小和渲染时间；
- 音频峰值、人声清晰度和响度提示；
- 字幕是否越过安全区；
- 目标平台配置是否与当前输出一致。

如果用户选择的格式不适合当前交换目标，系统要把任务拆开。例如：

- 剪映草稿：保留项目画布、帧率、素材引用，最终编码由剪映决定；
- FCPXML：导出时间线，不绑定 MP4/MOV 编码参数；
- MP4/MOV：按用户选择的编码、码率和音频参数渲染；
- 字幕：可选择烧录、独立字幕文件或两者同时输出。

### 6.4 导出界面和数据模型

导出界面分为两层：

- **快速导出**：选择平台预设、清晰度档位、字幕方式和输出目录；
- **高级导出**：展开完整参数，允许覆盖预设中的任意可用字段。

用户可以把当前参数保存为个人预设，例如“抖音口播高码率”“横版课程母版”“剪映交接包”。预设不是写死在代码里的常量，而是可版本化的 JSON 配置。

```json
{
  "name": "抖音口播高码率",
  "target": "render",
  "container": "mp4",
  "video": {
    "codec": "h264",
    "width": 1080,
    "height": 1920,
    "fps": "project",
    "rateControl": "vbr",
    "bitrateKbps": 16000,
    "hardware": "auto"
  },
  "audio": {
    "codec": "aac",
    "sampleRate": 48000,
    "channels": 2,
    "bitrateKbps": 192
  },
  "captions": {
    "mode": "burn-in"
  }
}
```

后端在创建导出任务前生成 `capability-report`：判断当前操作系统、GPU、FFmpeg、源素材和目标适配器是否支持这组参数。不可用组合必须给出“为什么”和“替代选项”，例如“当前显卡不支持 AV1 硬件编码，可切换软件编码或 H.265”。

导出任务应记录：参数快照、输入项目版本、使用的素材指纹、编码器、软件版本、输出文件校验和以及质量检查结果，保证成片可以追溯和复现。

## 7. 开源产品调研与借鉴边界

### ChatCut

开源 ChatCut 项目是 Premiere Pro 插件：由自然语言解析为带参数的编辑动作，例如缩放、滤镜、转场和模糊，并返回置信度；后端使用 FastAPI，前端使用 Adobe UXP，AI Provider 可替换。[ChatCut GitHub](https://github.com/akhil-datla/ChatCut)

可借鉴：

- 意图 → 类型化动作 → 编辑器命令；
- Provider 抽象；
- 批量操作；
- 对模糊指令先澄清，而不是猜测执行。

### OpenChatCut

OpenChatCut 更接近我们要做的 AI 剪辑底层：本地优先、真实多轨时间线、Agent Skills、MCP、Remotion/FFmpeg、MP4/SRT/FCPXML 和完整项目导出。它还采用 proposal → review → apply 的编辑事务模式，保证可预览、可撤销。[OpenChatCut 官网](https://openchatcut.com/)、[OpenChatCut GitHub](https://github.com/0xsline/OpenChatCut)

可借鉴：

- 一个 EditorCore 同时服务 UI Agent 和外部 MCP Agent；
- 编辑操作与界面解耦；
- proposal / approval / undo；
- 本地项目、素材和模型服务的分层；
- FCPXML、SRT、MP4 并列作为导出目标。

注意：OpenChatCut 使用 AGPL-3.0；不能直接复制代码后再以不兼容的闭源方式分发，后续若复用代码必须单独做许可证评估。[许可证说明](https://github.com/0xsline/OpenChatCut/blob/main/LICENSE)

### OpenCut

OpenCut 是 MIT 许可的跨 Web、桌面和移动端开源剪辑器，适合观察跨端工程组织和时间线架构；但其仓库当前仍在重构预览、特效和导出部分，不能直接视为成熟导出方案。[OpenCut GitHub](https://github.com/OpenCut-app/OpenCut)

## 8. 版本规划建议

### P0：先打通内容生产主链

- 账号、对标账号和选题对象；
- 结构化脚本编辑器；
- 分镜生成和 A 方案补拍任务；
- 本地素材导入、转写、标签和搜索；
- 主口播 + B-roll 的 AI 粗剪提案；
- 默认导出预设 + 自定义 MP4/MOV/SRT/素材包和项目清单；
- 内置 Agent / API / MCP 共用工具契约。

### P1：追平高频基础剪辑

- 自动去停顿和重复；
- 字幕样式；
- 基础花字和标题；
- 基础转场、BGM、音量压低；
- 9:16/1:1/16:9 多画布版本；
- 自定义分辨率、帧率、码率、编码器和音频参数；
- 剪映草稿适配器第一版；
- Windows/macOS 导出回归测试。

### P2：外部精修与复盘回流

- 剪映版本矩阵和兼容性检测；
- 有限的外部草稿读取；
- 成片回流和素材/脚本关联；
- 发布数据接入；
- 经验、风格和镜头偏好记忆；
- FCPXML 及更多编辑器适配。

### 暂缓

- 自建大规模模板/音乐/花字生态；
- 复杂动效编辑器；
- 软件控制手机或相机拍摄；
- 一开始就做剪映和本产品之间的双向无损同步；
- 直接复制剪映的商业素材和模板。

## 9. 当前最大技术风险

1. 剪映草稿格式非官方、版本敏感，且部分版本存在加密；
2. 花字、模板、字体和特效涉及资源 ID、授权和跨平台差异；
3. FCPXML 能表达通用时间线，但不能完整表达剪映特有花字和特效；
4. Windows/macOS 的路径、编码器和剪映本地目录不同；
5. AI 修改时间线必须具备可解释、可撤销和权限控制；
6. 本地素材和 API 密钥的隐私边界必须在架构层处理，而不是靠产品说明规避。

## 10. 下一步技术验证，不进入正式开发承诺

在 PRD 评审通过后，先做一个极小的“格式验证实验”，不做完整 MVP：

1. 用自有 Editing IR 描述 3 个视频片段、1 条口播音频、字幕和一个标题；
2. 在 Windows 和 macOS 各准备一个干净剪映项目；
3. 生成目标剪映草稿，验证能否打开、素材是否在线、轨道是否可编辑；
4. 同一份 IR 导出 FCPXML 和 MP4/SRT/manifest；
5. 记录每种格式保留和丢失的能力；
6. 决定剪映适配器首个支持的版本范围。

这个实验的成功标准不是“复制剪映所有能力”，而是验证：

> AI 生成的内容结构，能以可编辑、可检查、可回到创作系统复盘的方式进入用户已有的剪辑工作流。
